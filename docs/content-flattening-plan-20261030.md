# 病历内容扁平化方案（待负责人审核）

状态：**方案草案，未实施**。本 PR 只新增本文件，不改代码、医学正文、身份账本或发布配置。负责人批准本方案后，按第 5 节分 PR 实施；每个 PR 仍需单独授权合并。

## 1. 要解决的问题

病历正文目前由 `index.html` 里约 46 个脚本按顺序执行生成：`app.js`、`ideal-cases.js`、`orthopedic-expansion-a…g.js` 先建立记录，`record-quality-v3…v24.js`、`ortho-protocols-*.js`、`record-clinical-style-v25/26.js`、`record-course-v27.js`、`record-*-v28…v33.js` 再依次改写前面的结果。

问题：

- 想知道某条文书最终显示什么，必须把整条链跑一遍，单看任何一个文件都看不出来。
- Codex 改内容时容易改错文件，或者改动被后面的补丁覆盖。
- PR 审核时看到的是"补丁代码"的改动，不是"病历文字"的改动，医学审核很难逐句核对。
- 每加一轮修订就多一个 `vN` 文件，链越来越长。

## 2. 现状核查（2026-10-30，`main` @ 9e70c18）

- 生成链输出 5,381 条记录，分属 4 个科室、204 个病种分组（骨科 201 组，其余 3 科各 1 组）。
- 其中 5,377 条有固定正文（`sourceBody`）；只有 4 条是 `app.js` 按患者信息动态生成的通用场景（账本中 `bodyKind: generated-default`）。
- 全部记录序列化后约 6 MB JSON。
- 身份账本（`baseline.json`、`records.jsonl`）保存的是**原始身份和原始哈希**，不是正文来源；`revisions.json` 记录审核过的修订批次，并用 `sourceFiles`/`sourceSnapshotHash` 绑定生成链脚本的哈希。

结论：固定正文可以整体导出为数据文件，动态场景继续由代码生成。

## 3. 目标形态

```
content/clinical-library/
  baseline.json          ← 不动（原始身份锚点）
  records.jsonl          ← 不动
  revisions.json         ← 只追加；新增"源格式迁移"批次
  publication.json       ← 不动
  source/
    index.json           ← 分组顺序、groups/traumaGroups/seeds 等全局数据
    guke/<病种>.json      ← 每个病种一个文件，记录按原顺序排列
    puwai/…  shennei/…  fuke/…
```

每个病种文件就是一个数组，每条记录保留全部现有字段（`legacyId`/稳定 ID、`group`、`name`、`short`、`stage`、`type`、`desc`、`sourceBody`、特殊病例字段等），**字段值与当前生成链输出逐字节相同**。

以后改病历 = 直接改对应病种 JSON 里那一条的 `sourceBody`；PR 里看到的就是病历文字本身的差异。

`app.js` 保留界面代码和 4 个动态场景的生成函数（这部分仍算代码 + 内容混合，单独标注）。

## 4. 安全保证（迁移必须满足，否则不合并）

1. **逐条一致**：迁移前后对全部 5,381 条记录比较 `bodyHash`、`renderedHash`、`recordHash` 及所有字段，必须 100% 相同；构建产物中各科室目录与正文 JSON 文件内容（哈希命名）必须完全相同——即线上用户看到、复制、打印的内容一个字都不变。
2. **身份不变**：稳定 ID、数字 ID、病例归属、排序、名称、阶段、类型全部不变；`baseline.json`、`records.jsonl` 逐字节不变。
3. **审核链不断**：在 `revisions.json` 追加一条"源格式迁移"批次（不改正文，只把 `sourceFiles` 从生成链脚本切换为 `source/*.json`，并记录迁移前后的快照哈希），由负责人按现有 `--authorize` 流程授权。
4. **旧文件保留可追溯**：补丁脚本移入 `content/clinical-library/legacy-chain/`（不公开、不再参与构建），保留至少一个版本周期；Git 历史中始终可查。`record-quality-v2.js` 同样移入，不删除。
5. 现有全部测试、`audit:quality:check`、浏览器回归通过；依赖补丁脚本的单测改为针对 JSON 数据断言同样的医学事实。

## 7. 风险与回退

- 风险集中在步骤 C。由于有"两路构建必须完全相同"和逐条哈希校验，结果不一致时构建直接失败，不会上线错误内容。
- 若迁移后发现问题：撤回步骤 C 的 PR 即恢复旧链（账本只多一条迁移批次，再追加一条反向迁移批次即可，不删除记录）。

- 不在本方案范围：4 个动态场景的内容拆分、心电图/分型资料的数据化、CSS 合并——可以以后单独做。
