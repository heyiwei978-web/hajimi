# 稳定 ID 账本：受控正文更新流程

本流程已在 PR #25 实现。真实医学正文没有修改，`revisions.json` 的 `batches` 为空，没有应用真实修订或新增真实记录。演练仅使用内存及临时测试数据，不访问生产 Blob。

## 身份与版本

- `baseline.json`、`records.jsonl` 逐字节不变，保存原始病例成员、数字 ID、稳定 ID 和原始哈希。
- `scripts/clinical-baseline.mjs` 固定这两个文件的 SHA-256 及基准提交。缺失或改写即阻止构建；CLI 永久禁用 `--initialize`，必须从 Git 恢复原文件。
- `revisions.json` 只追加审核批次，包含上一账本摘要、旧/新正文及渲染和记录哈希、预览摘要、审核信息、旧源提交和候选源快照，不保存差异正文副本。
- 编译器重放修订得到当前内容版本，身份继承原始账本。新 ID 从历史最大数字 ID 后追加，不按当前数组位置编号；原始病例成员列表不改写，新成员只在派生状态中追加。
- 既有名称、病例归属、阶段、类型及其他非正文元数据冻结，变化需另做显式迁移。新增同名记录也被阻止，避免新的 CMS 歧义。

## 未来授权修改医学资料的操作流程

本任务没有执行真实更新命令。

1. 获得医学内容修改授权，在独立分支编辑源资料，保留原生成链。
2. 创建仅存本地的差异预览：

```bash
npm run audit:clinical -- --propose-update --output=/tmp/clinical-review.json
```

默认从当前 Git HEAD 读取旧源并验证其与已批准版本一致。若先提交了未经批准的新正文，使用 `--source-commit=<原已批准源的完整40位提交>` 指定旧源。浅克隆缺少旧对象时先获取历史，不能绕过旧哈希核对。

预览包含稳定 ID、旧/新精确哈希、逐行正文及默认渲染差异、新 ID、工作树源快照和账本版本。预览不更新账本。输出必须在仓库外，独占创建、权限 `0600`，拒绝覆盖已有文件或经符号链接写入仓库，避免进入公共资源。

3. 医学审核人检查完整差异、病例与生成影响后明确授权并记录依据。预览生成不等于医学批准。
4. 使用已审核的精确摘要更新：

```bash
npm run audit:clinical -- --apply-update=/tmp/clinical-review.json \
  --authorize='<已审核的proposalHash>' \
  --reviewed-by='<审核人>' \
  --reason='<授权修改原因>' \
  --review-reference='<医学审核记录编号>'
```

授权摘要、审核人、原因和依据全部必填。命令重新生成并比较预览，拒绝旧版本冲突、过期或篡改的预览、额外正文变化、改名、归属改变和缺失记录。全部校验后，仅原子追加一个修订批次，不改源正文、原始账本、发布政策或 CMS。

这些字段是本地显式操作与审计证据，不能代替医学人员审核、密码签名或在线身份认证；Git 审查仍是信任边界。

5. 运行审计、构建、单元和浏览器回归，将源资料与修订日志一起提交审核。`sourceCommit` 指向核验过的旧源，候选工作树由 `sourceSnapshotHash` 精确绑定，避免新提交引用自身 SHA。

## 新记录、特殊病例与 CMS

新文书必须具有完整身份字段和固定正文，目前只支持已有四科室。可向既有病例追加文书；新病例按明确的 `completeCaseKey` 或 `specialCaseKey` 独立归属。新增也先预览再授权，永不重排或复用已分配 ID。

两套 TKA 特殊病例及 `clinical-v1-r005159`、`clinical-v1-r005359`、`clinical-v1-r005360` 的旧名称和归属保留。可以按稳定身份审核正文版本，但不会移动、清空或重绑 CMS 覆盖、案例、图片。归档仍受独立发布政策和生产 CMS 门禁约束。

## 并发、故障与回滚

更新使用独占锁，写前再次核对磁盘版本、原文件、发布政策和日志前缀，只允许追加一个批次。先完整校验，再写临时文件、fsync、原子替换单一日志。普通失败不留半套账本，也不删除另一编辑者的锁。进程被强制终止留下锁时，应核对日志并确认无更新进程后人工清理。

本次没有真实修订，可撤回整个 PR。未来已分配永久 ID 的日志不得删除或截断；正文回滚应以旧正文作为新候选，再追加反向修订，保留 ID 高水位。不能只改哈希、删日志、重新初始化或用旧 Blob 覆盖新资料。
