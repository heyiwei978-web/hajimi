# 稳定 ID 账本：正文更新的维护缺口与解决方案

## 已确认的问题

当前确实存在维护缺口。本 Draft 只提出解决方案，没有修改正文、重建账本或放宽门禁。

`scripts/clinical-inventory.mjs:80` 固定文书数量；`:91` 起按病例归属、名称、短名、阶段、类型匹配身份，并要求记录全字段哈希、最终显示正文哈希与账本一致。因此正常修改一条正文也会阻止构建，改变共享生成函数也可能导致显示正文哈希失败。已有测试在内存中修改正文，已验证这一行为。

`scripts/audit-clinical-library.mjs:13` 的初始化在基线存在时拒绝覆盖，目前没有受控更新命令。删除账本后重新初始化会根据当时数组顺序重新分配 ID，可能破坏历史链接、收藏、CMS 和特殊病例关联，不能采用。直接手改多处哈希也缺少并发保护和内容修订审计。

现有内容未变化，构建通过；问题影响后续正常维护。建议在解除 Draft、准备合并前落实下述流程，或明确接受内容冻结限制并另立跟踪事项。

## 建议的最小兼容方案（尚未实施）

1. 保留 `baseline.json` 及原始 5,361 条哈希作为不可覆盖的历史快照，新增版本化的当前内容修订文件。
2. 身份与正文版本分离。已有 `recordId`、`legacyId`、`caseId` 永久继承账本；内容哈希只识别版本，不能重新分配身份。病例 ID 也不能因病例 key 改名而重新计算。
3. 未来提供 `audit:clinical --propose-update`，只输出按稳定 ID 对照的变更清单，不改文件；清单包含旧/新正文、显示正文及全记录哈希、账本版本、来源提交、原因和审核依据。未来的 `--apply-update <清单>` 仅在全部 expected-old 哈希和版本匹配时原子更新当前内容修订文件。以上参数是建议接口，当前脚本不支持。
4. 正文修改保持全部身份和病例成员。新增记录只从历史最大数字 ID 后追加，永不复用；改名、归属、阶段或类型变化要求显式 old→new 对照和专门审核，不能名称模糊匹配。归档独立走 `publication.json` 与生产 CMS 门禁。
5. 保持 CMS 名称键不自动迁移。同名、特殊病例和改名涉及的覆盖、案例、图片与引用先单独核验；账本更新不能清空或覆盖 Blob。
6. 源文件、修订文件及审核差异一起提交；先完整验证再写入，失败不留半套账本。回滚同时恢复对应源版本和修订文件，不能只回退哈希以强行通过构建。

建议修订字段：`recordId`、`expectedLedgerRevision`、`expectedRecordHash`、`previousBodyHash`、`nextBodyHash`、`nextRenderedHash`、`nextRecordHash`、`sourceCommit`、`reason`、`reviewReference`。版本使用递增值或修订文件摘要；不要要求提交在创建前把自己的 Git SHA 写入自身。可以绑定已审核的源提交。

## 后续实现验收（本 Draft 未完成）

- 授权修改一条合成正文，只改变该文书内容版本；原数字 ID、稳定 ID、病例 ID 及其他记录映射不变。
- 改正文后重排数组，身份和病例成员仍不变。
- 未授权变化、过期 expected-old、缺少审核、部分更新和并发冲突均失败且不写文件。
- 共享函数变化列出所有受影响的显示正文，包含 4 条动态场景；默认参数哈希不能替代不同患者输入的功能测试。
- 新增 ID 不复用；名称或病例归属变化必须显式审核；两套特殊病例和三条同名出院查房不得重新关联。
- 正文更新不能绕过归档门禁；同时回退源与修订文件能恢复原始哈希和构建。
