# 发布与核验流程

此文说明仓库的发布边界，不执行构建、部署或配置变更。当前实际线上状态以对应发布记录和平台核对为准。

## Git 连接与自动部署

GitHub 已连接 Vercel，但连接本身不代表每个分支都启用了自动部署。当前 `vercel.json` 的 `git.deploymentEnabled` 明确禁用以下四个分支：

- `main`
- `security/blob-static-token`
- `chore/clinical-library-slimming`
- `refactor/site-registry-phase1`

保留这些规则。代码审阅、Git 合并、创建暂存部署和正式入口切换是独立步骤，不能从某一步已获授权推导后续生产操作也已获准。其他分支的部署行为仍需单独核对，不在这里作全局禁用承诺。

## 使用已验证的源码与构建

1. 在独立本地候选中准备修改，保留病历身份、正文及安全边界。按修改范围完成现有构建和必要检查；已经通过且未受影响的检查不反复执行。
2. 上传前固定提交、来源清单及摘要，核对平台项目、变量元数据、保护和正式入口。环境变量值、账号密码、Cookie 和患者资料不放入仓库或报告。
3. 创建暂存部署需要独立的明确范围。使用 Production 变量的构建仍可能尚未成为正式版本；同时核实 production target 和正式域名的实际归属。
4. 暂存构建可能改变 Vercel 默认别名，必须记录实际变化并确认保护。不能用默认别名代替固定部署地址完成来源核验。

## 读取与写入证据分开

内容读取比较应同时检查响应结构、修订摘要和规范化公开内容摘要，不只比较 HTTP 状态。公开视图一致不证明未发布资料全集或完整 CMS 映射已审计。

网站管理员登录会建立管理会话，还可能真实改写生产登录限流记录。登录不是无副作用的读取；需要独立限定范围，不猜账号或通过重复登录补证。源码可能忽略限流写入异常，进入后台或返回 200 不能单独证明 Blob 写入成功，应结合完整前后对象元数据等正向证据。

状态码取自请求记录，运行错误取自运行日志，两类来源分列。某个窗口返回零条运行日志，只能说明当时未观察到异常，不代表应用记录了全部错误或历史缺口已经消除。

## 正式提升及停止条件

正式提升使用已验证的固定现有构建，避免用发布动作代替重新核验。提升前应明确切换目标、正式入口、默认别名允许的变化、只读验收数量和证据限制，并取得对应授权。

实际操作前取得新鲜前基线。提升后核对同一部署的状态、production target、所有正式入口、默认别名保护、配置/变量元数据、存储连接及部署清单；必要的只读请求与平台记录关联。退出码为零不能代替这些验收。

排队、部分切换、超时、错误或证据不足时，保存实际状态后停止。不要自动重复提升、修别名、重新部署或回退；客户端超时也可能发生在平台已经切换之后。

保留旧部署不等于已验证回退保障，尤其旧变量快照和凭据可能已经变化。回退应有独立范围和授权，不把旧构建仍存在当成安全保证。

## 历史记录与后续修改

G4 历史失败和 A7 日志观察限制按证据原样保留。后续读取、登录或提升通过时新增对应记录，不倒改历史失败，不把有限窗口观察升级为无保留通过。

真实手机、微信、自动浏览器和人工观察分别记录实际设备与方式，不相互冒充。测试、文档和发布收据分别说明各自覆盖范围。

本流程不授权病历编辑、身份台账迁移、凭据轮换、PR 清理或任何生产修改。新工作按明确范围推进，已使用的单次授权不复用。
